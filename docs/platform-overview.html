Hex · Architecture & development

Platform overview and local development

Run a complete Hex platform locally using filesystem providers or service containers, then deploy the same application against hosted services.

The local workflow supports a platform executable from another repository. Use hex dev for lightweight providers or optional PostgreSQL and Azurite services. No .NET or Azure account is required.

1. How the current platform works

There are two distinct things to test:

  • Hex itself: the framework, client, CLI, publishing protocol, and providers.
  • A particular Hex platform: your executable, chosen providers, configuration, and eventually custom integrations.

Server framework

server/ provides an HTTP handler configured with capability providers. Each capability is optional; omitting a provider disables its routes. 

handler := hex.New(hex.Config{
    Sites:    siteStorage,
    Files:    uploadStorage,
    Database: database,
    Realtime: realtime,
})
  • ObjectStore supplies uploaded application files.
  • SiteDirectory enumerates published directories without metadata.
  • Database supplies JSON document storage.
  • Realtime supplies subscriptions and broadcasts.

The framework does not provision infrastructure or implement authentication.

Static hosting and publishing

Publishing:
hex publish → configured provider → site storage (no Hex API calls)

Viewing:
Browser → site subdomain → NGINX → that site's files directly

The CLI synchronizes directly to a local directory or Azure Files using AzCopy. It does not request credentials, upload, register, or notify completion through Hex. The server only enumerates directories containing a root index.html. There are no site manifests, release archives, or metadata records. Folder synchronization is not transactional.

Each site has its own origin, such as https://demo.hex.example.com/. This separates localStorage, sessionStorage and IndexedDB. NGINX reads public/sites/demo/ for that hostname; shared /sites/demo/ web routes are not available.

Client, CLI, and hosting

  • @hex-platform/client exposes file operations, document CRUD, realtime channels, and capability discovery.
  • @hex-platform/cli initializes projects, installs the agent skill, publishes sites, lists sites, and unpublishes them.
  • Apps use same-origin requests to the gateway’s /api/ routes.
  • The Azure OpenTofu example adds Entra authentication, Container Apps, storage, and optionally PostgreSQL. These are deployment choices around the framework.

2. What already runs locally

A separate repository is not required to start testing. This repository includes a reference executable at cmd/hex-server and a development launcher that starts Go and NGINX. Install Go, Node.js, and NGINX, then run from the Hex repository: 

npm ci
npm run build
npm link --workspace @hex-platform/cli
npm run dev

In another terminal, initialize an app:

hex init my-app --server http://localhost:8080 \
  --publish-root /absolute/path/to/hex/.hex-data/sites/public/sites

From the generated app directory, publish it:

hex publish

Open my-app.localhost:8080/. 

localhost:8080 — NGINX
    ├── <site>.localhost → that site's local directory
    └── /api/*   → Go on localhost:8081
                       ├── In-memory app uploads
                       ├── In-memory documents
                       └── In-memory realtime

Published sites persist under .hex-data/. Application uploads and documents reset when the process restarts. Local development has no authentication and the listeners bind to loopback.

This tests the complete user workflow, including real WebSockets and direct NGINX serving. Set NGINX_BIN if NGINX is not on PATH.

For hosted subdomains, configure DNS, TLS bindings and Entra redirect URIs in the hosting layer. These are independent of file publishing. Direct Azure Files publishing requires the publisher's own storage authorization and network access to the private endpoint.

3. Local stand-ins for cloud services

A replacement provider tests Hex’s behavior. An emulator also exercises a cloud provider’s API and SDK integration. Both are useful, but they establish different things.

Recommended local equivalents
Production component Everyday development Provider testing
Azure Files for sites Local directory shared by Go and NGINX Optional local SMB share; real Azure for managed mounts
Azure Blob uploads In-memory object store Azurite to exercise the Blob SDK and provider
Azure PostgreSQL In-memory document database Optional local PostgreSQL with the same provider and schema
In-process realtime Same in-process provider Real WebSocket connections
Entra-managed ingress No authentication on loopback Separate hosted authentication tests

A local filesystem is sufficient to develop publishing, but does not prove Azure Files’ mount permissions, caching, or failure behavior. In-memory uploads test the Hex file API; Azurite tests the Azure Blob provider.

Available local tooling

  • The PostgreSQL provider already accepts a local connection through DATABASE_URL.
  • The CLI ships optional Docker Compose services for PostgreSQL and Azurite, with persistent volumes and readiness checks.
  • The Blob provider supports connection strings for Azurite. The Go development adapter initializes its upload container without requiring Azure credentials.
  • hex dev builds and launches your own repository or a prebuilt executable. npm run dev is a thin wrapper selecting this repository’s reference executable.

4. Developing in another repository

A platform built with Hex can have its own repository:

hex/
    Framework, providers, client, CLI, development tooling

my-company-hex/
    Go executable
    Provider selection and configuration
    Future custom integrations
    Deployment composition

my-hex-app/
    Frontend application

While developing both Go repositories, add a local module replacement to the platform’s go.mod: 

replace github.com/crazycatviking/hex => ../hex

Alternatively, use a local go.work workspace containing both modules. Changes to the framework can then be tested without publishing a release.

For a bundled frontend, build the client and install it from its local directory, adjusting the path to match your checkout: 

npm install ../hex/packages/client

The static starter receives a copy of the built client JavaScript during initialization. That copy does not automatically track later changes to the client package.

Keep the platform executable the same between local and hosted environments. Configuration selects provider implementations and service endpoints.

5. Recommended development environment

The CLI provides two modes for consuming repositories. Import server/dev in your local server configuration, then run hex dev. The production HTTP framework remains independent.

Lightweight mode

NGINX + your platform executable
    ├── Local site directory
    ├── In-memory app uploads
    ├── In-memory database
    └── In-process realtime

This is the default: no Azure account, Docker, PostgreSQL or Azurite service is needed. Site files remain on disk for NGINX; application uploads and documents reset on restart.

Service-backed mode

NGINX + your platform executable
    ├── Local site directory
    ├── Azurite Blob Storage
    ├── PostgreSQL container
    └── In-process realtime

Run hex dev --services postgres,azurite, or select just one service. Docker Compose supplies persistent volumes and health checks. The local Go adapter supplies repeatable initialization.

The launcher accepts:

  • The platform repository or executable to run.
  • Its environment configuration.
  • The shared site directory.
  • Gateway and API ports.

This keeps local tooling useful outside the Hex repository.

6. Testing each part

  1. Unit and provider-contract tests. Validate the same storage and database semantics against each implementation.
  2. Local integration tests. Run the platform, NGINX, CLI, client, PostgreSQL, and Azurite together. Test persistence across restarts, publishing, downloads, pagination, and WebSockets.
  3. Hosted smoke tests. Verify Entra rejection of anonymous requests, private networking, managed identity, and Azure Files mounting—properties local stand-ins cannot establish.

Checks available today

go test -race ./...
go vet ./...
npm run build
npm test
npm run test:e2e
npm run test:local
npm run test:services

The existing end-to-end test uses the local providers and real NGINX. It exercises publishing, file operations, documents, WebSockets, and static serving after the Go process stops. Additional tests build an independent consuming Go module and verify its custom endpoint, local configuration, restart persistence and process cleanup. Service-backed tests exercise real PostgreSQL and Azurite through the Go providers.

Get started: copy the custom-server example into your own Go module and run hex dev. See the local development guide for configuration, optional services and the environment contract.
